# 皓量云擎业务管理系统后端开发规范

## 适用范围

本文件适用于 `backend/` 及其所有子目录，并继承仓库根目录 `AGENTS.md`。子目录若存在更具体的 `AGENTS.md`，继续叠加执行。

## 技术栈与目录边界

- 使用 PHP 8.4、Webman、MySQL 8.0 和 Redis。
- `app/`：后端应用源码；核心业务采用模块化单体组织，不得为追求“可插拔”而把产品、订单、客户、财务、营销和履约等核心能力全部插件化。
- `app/modules/`：按业务能力划分的模块目录。安装、会员、商品目录、定价、订单、支付、履约、财务、营销和渠道等能力分别收拢在自己的模块内。
- `app/shared/`：真正跨模块且语义稳定的公共能力；不得把特定业务规则或仅被单个模块使用的代码放入该目录。
- `app/controller/`、`app/middleware/`、`app/exception/`、`app/process/` 和 `app/queue/`：仅保留全局入口及跨模块运行时能力；模块专属代码必须放回对应模块。
- `plugin/`：Webman 应用插件目录，仅承载可独立安装、升级、禁用和卸载的扩展。
- `themes/`：官网主题模板源码；主题静态资源发布到受控的公开目录。
- `public/`：唯一公开文件边界；配置、模板源码、私有上传、日志和迁移不得放入该目录。
- 禁止直接修改 `vendor/`、`runtime/` 及其他框架或工具生成内容。
- `public/app/` 与 `public/install-assets/app/` 是前端构建产物，必须由对应 Vite 应用生成；发行版需要提交这些产物，确保服务器无需 Node.js 即可运行。
- `public/install-assets/vendor/` 保存安装器离线依赖，更新版本时应从明确的官方分发地址重新获取并核验版本，不在运行时使用 CDN。

## 架构与依赖规则

后端采用“模块化单体 + 选择性 DDD”。目录首先按业务模块划分，再按实际复杂度决定模块内部是否需要领域层，不得为了形式完整而给每个模块机械创建空层或无业务意义的实体、仓储和领域服务。

```text
app/
├── modules/
│   └── <module>/
│       ├── controller/       模块 HTTP 入口、参数接收和响应转换
│       ├── application/      用例编排、事务边界和应用服务
│       ├── domain/           按需使用的实体、值对象、领域服务和领域事件
│       ├── contract/         Repository、Gateway 和外部能力接口
│       ├── infrastructure/   数据库、Redis、队列和第三方接口实现
│       ├── exception/        模块业务异常及异常映射
│       └── middleware/       仅作用于本模块的中间件
├── controller/               全局页面或跨模块 HTTP 入口
├── middleware/               全局横切中间件
├── exception/                全局异常与异常处理器
├── process/                  Webman 自定义进程
├── queue/                    跨模块队列运行入口
└── shared/                   跨模块且稳定的公共能力
```

- 简单配置、查询和普通 CRUD 可以使用 Controller、Application、Contract 与 Infrastructure 的精简结构；只有存在状态流转、不变量、复杂计算或多对象协作时才引入完整 Domain 模型。
- 产品销售配置、条件定价、订单状态、支付退款、账务、履约、上下游同步、优惠活动、返利和结算等核心复杂领域应使用实体、值对象、领域服务及领域事件保护业务规则。
- Controller 只负责 HTTP 边界，不直接访问 Model、数据库、Redis 或第三方接口，必须调用本模块的 Application 用例。
- Domain 不得依赖 `Request`、`Response`、`Db`、`Redis` 或其他 Webman/Illuminate 基础设施类，也不得依赖 Controller、Application 或 Infrastructure。
- Application 可以依赖本模块的 Domain 和 `contract/` 接口，不依赖 Infrastructure 具体实现；Infrastructure 实现 Contract 并通过容器完成绑定。
- 新增持久化 Model 应放在对应模块的 `infrastructure/` 内；不得继续把核心业务 Model 堆放到全局 `app/model/`。
- 跨层复杂数据优先使用明确的 DTO、值对象和接口；只读、局部且结构稳定的简单结果可以使用带精确 PHPDoc array shape 的数组。
- 模块之间禁止直接访问对方的 Model、Repository 实现或数据表；同步协作通过对方 Application 门面或公开 Contract，异步副作用通过领域事件或应用事件完成。
- 涉及支付成功、订单状态与履约调度等“数据库提交后必须可靠执行”的事件，必须评估事务 Outbox、幂等消费、重试和补偿，不能依赖内存事件保证可靠性。
- `shared/` 不能反向依赖具体业务模块；仅被一个模块使用的代码保留在该模块内部，避免形成万能公共层。
- 核心领域不得出现供应商专属字段；产品销售契约、连接器能力、履约字段与供应商参数通过版本化契约和映射规则衔接。
- 社区版、专业版和企业版共用同一套领域代码，通过稳定的功能授权、能力声明和许可证策略控制，不维护三套长期分叉代码。
- 当前阶段保持单体部署和单一安装包；只有出现明确的独立扩缩容、独立数据边界或团队自治需求时，才评估将成熟模块拆分为服务。

## PHP 与 Webman 规范

- PHP 文件使用 `declare(strict_types=1);`，参数、属性和返回值必须声明类型。
- 类默认声明为 `final`；不可变数据优先使用 `readonly`。
- `app/` 下目录统一使用小写，多单词目录使用下划线；命名空间必须与目录一致。
- 遵循 PER Coding Style，保持单一职责和可测试性，避免无业务语义的超大 Service 或工具类。
- Webman 是常驻内存、多进程应用，不得把请求、当前用户、Session、事务或租户状态保存在静态属性、单例或全局变量中。
- 常驻对象持有的连接、缓存和监听器必须明确生命周期，避免跨请求数据泄漏和重复注册。
- 配置、进程定义、Composer 依赖或启动期加载内容变更后，必须说明是否需要 reload/restart，不得假设热更新自动生效。

## 复用与工具类规范

- 多处重复且语义稳定的通用操作可以封装为工具类或公共服务，避免复制粘贴；封装前应确认输入、输出、异常和副作用边界清晰，不能仅因代码片段看起来相似就过早抽象。
- 纯计算、格式转换、脱敏、编码等无状态逻辑可以放入职责单一的工具类；涉及数据库、Redis、文件、网络、日志、配置或时间等外部依赖的操作必须封装为可注入服务，并通过构造函数显式注入依赖。
- 业务规则不得迁入通用工具类。产品定价、订单状态、退款资格、权限判断和履约决策等规则应保留在对应 Domain 或 Application 层；数据库及第三方调用仍应遵循 Contract 与 Infrastructure 边界。
- 工具类放置位置必须服从作用域：仅供单个业务域使用的能力放在该领域内部；真正跨领域且稳定的能力才放入 `app/shared/`。不得创建无明确职责的 `CommonUtil`、`Utils`、`Helper` 或万能公共类。
- 工具类和公共服务必须使用表达业务含义的类名与方法名，保持小而专一；不得通过动态数组、全局变量或隐式上下文隐藏必要参数。
- 只有无状态、无副作用的纯函数或命名构造器可以使用静态方法；存在依赖或副作用的可复用操作必须使用实例方法和依赖注入，以便替换与测试。
- Webman 常驻进程中的工具类和公共服务不得缓存当前请求、用户、Session、租户、事务或其他请求级可变状态，避免跨请求数据泄漏。
- 新增可复用能力时应补充 PHPDoc 和针对输入边界、异常路径及副作用的单元测试；修改公共行为前必须搜索全部调用方并评估兼容性。

## 注释与 PHPDoc 规范

- 在类、接口、枚举、公共方法、受保护方法、复杂数据结构和关键业务规则上补充 PHPDoc，说明职责、输入输出、业务约束、副作用、异常及并发或常驻内存注意事项；私有方法存在复杂逻辑或非显然约束时也必须补充。
- PHPDoc 统一采用 PhpStorm 默认的完整标签式格式和标准 `/** ... */` 结构：首行写摘要；仅有摘要时，下一行直接书写标签，不得在摘要与标签之间保留空白注释行；确有详细描述时，摘要后空一行书写详细描述，再空一行书写标签。
- 已声明原生参数和返回类型的方法，PHPDoc 仍必须完整列出每个 `@param` 和 `@return`，不得以“与原生类型重复”为由省略；无返回值的方法使用 `@return void`，构造函数按照 PhpStorm 默认格式只列参数而不写 `@return`。
- 每个 `@param` 必须包含准确类型、变量名和参数业务含义；`@return` 必须包含准确类型，并在返回含义不直观时写明说明。同一注释块存在多个参数时，类型和变量名列按 PhpStorm 默认格式对齐。
- 方法可能主动抛出或透传调用方需要处理的异常时，必须使用 `@throws` 写明异常类及触发条件；不得记录实际上不会抛出的异常，也不得遗漏稳定公开 API 的异常契约。
- 根据实际需要准确使用 `@var`、`@template`、`@extends`、`@implements`、`@deprecated` 和 `@see` 等标签。
- 数组、集合、回调和泛型无法由原生类型完整表达时，必须使用 PHPDoc 标明 array shape、元素类型、键类型、回调签名或模板类型，不得只写含糊的 `array`、`mixed`。
- PHPDoc 不能替代 PHP 原生类型声明；参数、属性和返回值仍须使用尽可能精确的原生类型，文档负责补充业务语义和静态分析信息。
- 行内注释优先解释“为什么这样做”、兼容边界、事务或幂等策略和不直观的算法，不要逐行复述代码，也不要保留大段已注释掉的废弃代码。
- 注释必须与实现同步更新；无法确认、已经过期或可能误导维护者的注释应立即修正或删除。

标准示例：

```php
/**
 * 校验用户是否满足指定年龄要求。
 * @param string $name 用户名
 * @param int    $age  年龄
 * @return bool 是否满足要求
 * @throws InvalidArgumentException 年龄小于零时抛出
 */
```

存在详细描述时的示例：

```php
/**
 * 校验用户是否满足指定年龄要求。
 * 用户名会先去除首尾空白；年龄必须为非负整数。
 * @param string $name 用户名
 * @param int    $age  年龄
 * @return bool 是否满足要求
 * @throws InvalidArgumentException 年龄小于零时抛出
 */
```

## 插件规范

- 普通项目内模块放在 `app/modules/`；只有具备独立安装包、版本和生命周期的能力才放入 `plugin/`。
- 插件标识仅使用小写字母、数字和下划线，发布后不得随意修改。
- 插件必须通过 Core 定义的 Contract、事件和 DTO 交互，不得直接修改核心领域对象、核心表结构或依赖内部实现类。
- 每个插件必须声明唯一 ID、版本、系统兼容范围、插件类型、权限、依赖、入口、迁移、静态资源及卸载数据策略。
- 插件安装包不得包含 `.env`、密钥、生产连接信息、日志、测试上传物、依赖目录或前端源码依赖树。
- 插件涉及前端时，客户服务器只安装预构建产物，不执行 `npm install` 或现场编译。
- 表单、产品参数和普通列表优先使用 Schema UI；小型扩展使用受控 Slot；复杂独立页面使用隔离 iframe 与稳定 SDK 通信。
- 插件安装、升级和卸载脚本属于高风险变更，必须考虑幂等、事务或补偿、失败恢复、版本兼容和明确的数据保留策略。
- 应用商店分发经过构建、校验和签名的不可变安装包，不直接分发工作区源码。

## 主题规范

- 主题目录使用 `themes/<theme_id>/`，至少包含主题清单、模板、静态资源和预览图。
- 主题 ID 和模板名称必须通过白名单解析，禁止将请求参数直接拼接为模板路径。
- 第三方主题不得包含可执行 PHP 文件；模板变量默认转义，未经净化的数据不得使用 raw 输出。
- 主题模板不放入 `public/`；只有需要公开访问的版本化静态资源才能发布到公开目录。
- 主题上传和安装必须校验文件类型、路径穿越、压缩炸弹、版本兼容和完整性。

## 数据与安全

- 金额统一使用整数最小货币单位存储和计算，不使用浮点数参与结算。
- 数据库迁移必须可审查；不可逆变更需提供备份、灰度、前向修复或回退说明。
- 日志不得记录密码、Authorization、Cookie、完整支付数据和未脱敏个人信息。
- 所有运营后台、会员和插件接口必须分别完成认证、权限及对象归属校验。
- 上传、插件包和主题包必须校验内容、扩展名、MIME、大小、存储路径与访问权限，不能仅信任客户端元数据。
- 调用上游供应商和支付、短信、实名等外部服务时，必须设置超时、重试边界、幂等键、审计日志和脱敏策略。

## 接口返回与异常处理规范

- 所有 `/api` 接口（包括 Controller、中间件、异常处理器和插件接口）统一使用 `app/shared/http/ApiResponse.php` 生成 JSON，禁止手写 `json_encode()`、直接调用 `json()`，也不得自定义另一套响应字段。
- 响应固定包含 `code`、`message`、`data`、`request_id` 四个字段；响应头必须同步返回 `X-Request-Id`。成功时 `code` 必须为 `0`；失败时 `code` 必须为稳定且非零的业务错误码，`data` 没有内容时为 `null`，不得省略固定字段。
- 成功响应示例：`{"code":0,"message":"ok","data":{},"request_id":"..."}`。失败响应示例：`{"code":42200,"message":"参数校验失败","data":{"errors":{"name":["名称不能为空"]}},"request_id":"..."}`。
- HTTP 状态码表达协议层结果，业务错误码表达可供程序判断的失败原因，二者不得混用。禁止“所有请求都返回 HTTP 200”；常用状态为 400 参数格式错误、401 未认证、403 无权限、404 资源不存在、409 状态冲突、422 业务或字段校验失败、423 资源锁定、429 请求过多、500 未预期异常、503 服务不可用。
- 通用错误码定义在 `app/shared/http/ApiErrorCode.php`，默认采用五位编码；具体业务域可以定义更细的稳定错误码，但发布后不得改变已有错误码的语义，也不得把数据库错误号、第三方原始错误码或异常行号直接作为接口错误码。
- 可预期且可安全展示的失败统一抛出 `app/exception/BusinessException.php` 或其语义明确的子类。Controller 不得为每个业务异常重复 `try/catch`，由 `app/exception/Handler.php` 统一转换响应。
- 字段校验错误放入 `data.errors`，键为稳定字段名，值为字符串数组；批量操作错误放入 `data.items` 并携带业务对象标识。不得只拼接一段无法被前端定位字段的文本。
- 基础设施层捕获 PDO、Redis、网络、支付或供应商 SDK 异常时，必须使用 `$previous` 保留异常链，再转换为本系统异常；不得把连接串、SQL、密钥、第三方响应原文或堆栈暴露给客户端。
- 未预期异常必须由全局异常处理器记录完整服务端日志，API 仅返回错误码 `50000` 和通用提示，生产或调试环境都不得在接口中返回堆栈、文件路径、SQL、配置或密钥。
- 业务异常属于预期分支，默认不写系统错误日志，避免污染告警；登录失败、越权、支付、退款等安全或资金事件必须另写脱敏的审计日志。禁止空 `catch`、吞掉异常或仅记录日志后继续返回成功。
- 日志必须携带同一请求的 `request_id`、HTTP 方法、路径和必要的脱敏业务标识；不得记录密码、令牌、Cookie、Authorization、完整身份证号、银行卡号或第三方密钥。不得将查询字符串整体写入异常日志。
- 外部服务错误必须在 Infrastructure 边界转换为本系统稳定错误码和用户可理解的信息；原始异常只留在服务端日志。重试耗尽、熔断、超时和幂等冲突要使用不同错误码，便于监控和前端处理。
- 新增或修改接口时，至少测试成功响应、业务异常、权限/状态异常和未预期异常，断言 JSON 固定字段、HTTP 状态码、业务错误码及 `X-Request-Id`；不得只断言提示文字。

## 后端验证

根据变更范围选择并执行：

```bash
composer validate --no-check-publish
find app config support -type f -name '*.php' -print0 | xargs -0 -n1 php -l
vendor/bin/phpunit
```

- 修改路由、中间件、进程、事件、队列或定时任务时，补充对应的集成验证，并关注多进程及常驻内存行为。
- 修改数据库、Redis、外部接口或插件生命周期时，验证失败路径、幂等性和恢复策略，不能只覆盖成功路径。
- 无法运行依赖真实服务的检查时，明确列出未验证项和所需环境，不得用 Mock 或静态检查代替生产集成结论。
